# STAGE 4 — `/scan`, Atomic Admission & Manual Fallback

Follow `THW26_RULES.md`. Start only after the owner approved Stage 3. This is the most important stage for event-day reliability. Keep what already works; fix what the audit found wrong.

## Goal

Several staff, each on their own phone, scan individual passes at the same time. Every admission is recorded exactly once, with the staff member and a server timestamp, and the entrance takes a few seconds per person.

## Requirements

### 1. One admission function (single source of truth)
Create or confirm a single server-side/database operation, e.g. `admit_pass(token)`, used by **every** admission path:
1. Caller must be an authenticated, **active** staff or admin account.
2. Look up the pass by token. Unknown/invalid → rejected (generic response; don't reveal whether a token ever existed).
3. Check pass status (not revoked) and registration status (approved).
4. Mark the pass admitted **atomically** with a conditional update or row lock, e.g. `UPDATE … SET admitted_at = now(), admitted_by = <staff> WHERE id = … AND status = 'issued' AND admitted_at IS NULL RETURNING …`. Only one concurrent caller can win.
5. Insert the admission log (attendee, household, staff member, server time, method) in the same transaction.
6. Return one clear result code.

Result codes the UI must handle:
| Code | UI |
| --- | --- |
| `admitted` | **Green** — Entry approved: attendee name, household, "x of y arrived" |
| `invalid` / `revoked` | **Red** — Invalid or revoked pass |
| `already_used` | **Yellow** — Already checked in: previous time and who admitted them |
| `needs_attention` | **Warning** — Registration requires administrative attention |
| network/server failure | **Error** — "Not confirmed. Do NOT admit. Check connection and rescan." |

The arrival time is generated by the server, never by the phone.

### 2. Reconcile the two admission systems
The older `/check-in` flow counts people per household; `/scan` admits individual passes. Make sure both feed the **same** invariant: total admitted for a household can never exceed its approved capacity, and one person can't be counted twice. Either route the household-count flow through the same function/table, or make it clearly manual-fallback only. Explain what you chose and show the SQL/constraint that guarantees the invariant. Keep `/check-in` working and keep its existing history.

### 3. Manual fallback
- Staff can search registered attendees by name or household, select one, and admit them through the **same** admission function (by attendee id).
- It must respect revocation, capacity and already-admitted rules exactly like scanning.
- A guest who is on the approved list but not registered gets the **warning** state, not a silent admit. Do not build on-the-spot registration unless the owner asks; list it as a question.

### 4. Scanner UX (mobile)
- Opens at `/scan` after staff login; camera starts immediately; handles the permission prompt and denial with clear help. Works over HTTPS on Android Chrome and iPhone Safari.
- Debounce repeat reads of the same code so one pass is never submitted many times per second.
- After each result, a large clear colour state; one tap (or an auto-reset after a few seconds) returns to scanning for the next guest.
- Show the staff member's name and a link to manual search. No unnecessary navigation or animation.
- Never display success unless the server returned `admitted`.

### 5. Concurrency & load tests (against a staging/test database, never production)
- 20 parallel requests with the **same** token → exactly one `admitted`, the rest `already_used`, one log row.
- 5 staff accounts scanning 100 different valid tokens in parallel → 100 `admitted`, 100 log rows, no errors, counts consistent.
- Same attendee admitted via scan and via manual fallback at the same time → exactly one admission.
- Revoke a pass during scanning → next scan is red.
- Disabled staff cannot admit even with a live session.
- Simulate network failure → UI shows the error state and no log row exists.
Show the commands and output.
